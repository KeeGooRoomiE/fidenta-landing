## Технологии

| Технология | Версия | Для чего |
|---|---|---|
| [Astro](https://astro.build/) | 5.x | Основной фреймворк, сборка, маршрутизация |
| [Tailwind CSS](https://tailwindcss.com/) | 4.x | Утилитарные CSS-классы |
| [TypeScript](https://www.typescriptlang.org/) | 5.x | Типизация JS/TS-кода внутри `.astro` и `.ts` |
| [pnpm](https://pnpm.io/) | 9.x | Пакетный менеджер (быстрее npm, строгие зависимости) |
| Python | 3.x | Скрипт отправки CTA-заявок по почте |
| GitHub Actions | — | CI/CD: сборка, тесты, деплой, уведомления |
| GitHub Pages | — | Хостинг статики |

> **Почему Astro?**  
> Astro генерирует чистый HTML без JavaScript на клиенте там, где он не нужен.  
> Компоненты пишутся в синтаксисе `.astro` — это смесь HTML и JS/TS в одном файле.  
> Для лендинга это идеально: быстрая загрузка, SEO из коробки.

## Ветки и окружения

Проект живёт в трёх постоянных ветках, каждая имеет свой задеплоенный URL.

| Ветка | URL | Назначение |
|---|---|---|
| `main` | `https://keegooroomie.github.io/fidenta-landing/` | Стабильная продакшн-версия |
| `stage` | `https://keegooroomie.github.io/fidenta-landing/stage/` | Версия для демонстрации клиенту |
| `dev` | `https://keegooroomie.github.io/fidenta-landing/dev/` | Рабочая ветка команды разработки |

### Поток изменений

```
feature/имя-фичи  →  dev  →  stage  →  main
```

- **`feature/*`** — отдельная ветка для каждой новой фичи или компонента.  
  Деплой не триггерится. Ветка живёт только в процессе работы.
- **`dev`** — основная рабочая ветка. Сюда вливаются все фичи через Pull Request.  
  Автоматически деплоится на `/dev/` при каждом push.
- **`stage`** — стабилизированная версия для показа клиенту.  
  Обновляется вручную из `dev` после проверки. Деплоится на `/stage/`.
- **`main`** — финальная версия вертикального среза.  
  Обновляется из `stage` после подтверждения клиентом. Деплоится на корень `/`.

> Фичи всегда создаются от `dev` и вливаются обратно в `dev`.  
> Никогда не пушьте напрямую в `stage` или `main` — только через PR.

## Быстрый старт

### Предварительные требования

- [Node.js](https://nodejs.org/) v20 или выше
- [pnpm](https://pnpm.io/installation) v9 или выше

Проверить установленные версии:
```bash
node --version   # должно быть v20.x.x или выше
pnpm --version   # должно быть 9.x.x или выше
```

Если pnpm не установлен:
```bash
npm install -g pnpm
```

### Установка

```bash
# 1. Клонировать репозиторий
git clone https://github.com/keegooroomie/fidenta-landing.git

# 2. Перейти в папку проекта
cd fidenta-landing

# 3. Переключиться на рабочую ветку
git checkout dev

# 4. Установить зависимости
pnpm install
```

> **Что делает `pnpm install`?**  
> Читает файл `package.json`, скачивает все нужные пакеты в папку `node_modules/`  
> и фиксирует точные версии в файл `pnpm-lock.yaml`.  
> `pnpm-lock.yaml` всегда коммитится в репозиторий — это гарантирует,  
> что у всех членов команды будут одинаковые версии пакетов.

### Запуск

```bash
pnpm dev
```

Откройте браузер: [http://localhost:4321](http://localhost:4321)

## Команды

Все команды запускаются из корня проекта.

| Команда | Что делает |
|---|---|
| `pnpm install` | Устанавливает зависимости из `package.json` |
| `pnpm dev` | Запускает локальный сервер разработки на `localhost:4321` с hot-reload |
| `pnpm build` | Собирает проект в статические файлы в папке `dist/` |
| `pnpm preview` | Запускает локальный сервер для просмотра собранного `dist/` |
| `pnpm astro check` | Проверяет TypeScript-типы и синтаксис в `.astro` файлах |
| `pnpm astro add <интеграция>` | Устанавливает и настраивает интеграцию Astro (например, tailwind) |
| `pnpm lint` | Запускает линтер кода (ESLint) |

### Подробнее о `pnpm dev` vs `pnpm build`

**`pnpm dev`** — режим разработки:
- Запускает сервер, который следит за изменениями файлов
- При изменении файла — автоматически обновляет страницу в браузере (hot-reload)
- Не оптимизирует код — сборка быстрая, но не для продакшна
- Файлы не записываются на диск — всё в памяти

**`pnpm build`** — продакшн-сборка:
- Генерирует оптимизированные HTML/CSS/JS файлы в папке `dist/`
- Минифицирует код, убирает лишнее, оптимизирует изображения
- Именно этот `dist/` деплоится на GitHub Pages
- После сборки можно просмотреть результат через `pnpm preview`

## Архитектура компонентов

Компоненты организованы по принципу убывающей ответственности: от общего к частному.

### Иерархия (4 уровня)

```
┌─────────────────────────────────┐
│  Layout.astro                   │  ← Уровень 1: Лейаут
│  (HTML-оболочка, <head>, шрифты)│
│  ┌───────────────────────────┐  │
│  │  index.astro (Page)       │  │  ← Уровень 2: Страница
│  │  (собирает блоки вместе)  │  │
│  │  ┌─────────────────────┐  │  │
│  │  │  Hero.astro (Section)│  │  │  ← Уровень 3: Блок/Секция
│  │  │  (логика блока)      │  │  │
│  │  │  ┌───────────────┐   │  │  │
│  │  │  │ Button.astro  │   │  │  │  ← Уровень 4: UI-элемент
│  │  │  │ (атом)        │   │  │  │
│  │  │  └───────────────┘   │  │  │
│  │  └─────────────────────┘  │  │
│  └───────────────────────────┘  │
└─────────────────────────────────┘
```

### Уровень 1 — Layout (`src/layouts/Layout.astro`)

**Отвечает за:** HTML-скелет, общий для всех страниц.

Содержит:
- `<!DOCTYPE html>`, `<html>`, `<head>`, `<body>`
- Подключение глобального CSS
- Подключение шрифтов
- Мета-теги SEO (title, description)
- `<slot />` — место, куда Astro вставляет контент страницы

```astro
---
// Всё между --- это frontmatter: JS/TS код, который выполняется на сервере при сборке
interface Props {
  title: string;
  description?: string;
}
const { title, description = 'Fidenta — продажа и аренда недвижимости' } = Astro.props;
---

<!doctype html>
<html lang="ru">
  <head>
    <meta charset="UTF-8" />
    <title>{title}</title>
  </head>
  <body>
    <slot />  <!-- Сюда вставится контент страницы -->
  </body>
</html>
```

### Уровень 2 — Страница (`src/pages/index.astro`)

**Отвечает за:** сборку страницы из секций.

Страница импортирует Layout и все нужные секции, выстраивает их в правильном порядке.  
Никакой бизнес-логики — только импорты и разметка.

```astro
---
import Layout from '../layouts/Layout.astro';
import Header from '../components/sections/Header.astro';
import Hero from '../components/sections/Hero.astro';
import Footer from '../components/sections/Footer.astro';
---

<Layout title="Fidenta — Недвижимость">
  <Header />
  <main>
    <Hero />
    <!-- Новые блоки добавляются здесь -->
  </main>
  <Footer />
</Layout>
```

### Уровень 3 — Секция/Блок (`src/components/sections/`)

**Отвечает за:** логику и разметку конкретного блока страницы.

Каждая секция — самодостаточный блок: знает свою структуру, использует UI-элементы.  
Пример: `Hero.astro` содержит заголовок, подзаголовок, кнопку CTA и фоновое изображение.

### Уровень 4 — UI-элемент (`src/components/ui/`)

**Отвечает за:** один переиспользуемый элемент интерфейса.

Максимально "тупые" компоненты: принимают props, рендерят разметку.  
Не знают контекст — одна кнопка используется и в Hero, и в Header, и в других блоках.

### Синтаксис `.astro` файла

```astro
---
// FRONTMATTER — выполняется на сервере (Node.js) во время сборки
// Здесь: импорты, JS/TS логика, работа с данными
import SomeComponent from './SomeComponent.astro';
const message = "Привет!";

// Типизация пропсов (Astro использует TypeScript)
interface Props {
  title: string;
  variant?: 'primary' | 'secondary';
}
const { title, variant = 'primary' } = Astro.props;
---

<!-- TEMPLATE — HTML-разметка компонента -->
<!-- Используем {фигурные скобки} для вставки JS-выражений -->
<div class={`button button--${variant}`}>
  <span>{title}</span>
  <SomeComponent />
</div>

<style>
  /* СТИЛИ — скопированы в <style> тег в HTML, изолированы по умолчанию */
  .button {
    padding: 12px 24px;
  }
</style>

<script>
  /* КЛИЕНТСКИЙ JS — выполняется в браузере пользователя */
  document.querySelector('.button')?.addEventListener('click', () => {
    console.log('Клик!');
  });
</script>
```

## Стили и Tailwind

Проект использует два подхода к стилям — они дополняют друг друга:

### 1. Глобальный CSS (`src/styles/global.css`)

Содержит:
- CSS-переменные (цвета бренда, типографика, отступы)
- Сброс стилей браузера (CSS reset)
- Базовые стили для `body`, `html`
- Стили, которые нужны везде

```css
:root {
  --color-primary: #1A3B5C;
  --color-accent: #E8A000;
  --font-heading: 'Montserrat', sans-serif;
  --font-body: 'Inter', sans-serif;
}
```

### 2. Tailwind CSS (утилитарные классы)

Tailwind генерирует CSS из классов, которые ты используешь в разметке.  
Вместо написания отдельного CSS-класса — применяешь готовые утилиты прямо в HTML:

```html
<!-- Без Tailwind: нужно писать CSS отдельно -->
<button class="cta-button">Оставить заявку</button>

<!-- С Tailwind: стили прямо в классах -->
<button class="px-6 py-3 bg-primary text-white rounded-lg hover:opacity-90 transition">
  Оставить заявку
</button>
```

> `px-6` = `padding-left: 1.5rem; padding-right: 1.5rem;`  
> `py-3` = `padding-top: 0.75rem; padding-bottom: 0.75rem;`  
> `hover:opacity-90` = при наведении прозрачность 90%

## GitHub Actions — воркфлоу

Все воркфлоу находятся в `.github/workflows/`. Каждый отвечает за одну задачу.

### `deploy.yml` — Деплой на GitHub Pages

**Триггер:** push в `main`, `stage` или `dev`

При пуше в любую из трёх основных веток:
1. Устанавливает зависимости
2. Собирает проект с нужным `base` path (зависит от ветки)
3. Публикует `dist/` в соответствующую папку на GitHub Pages

> **Почему разные base paths?**  
> GitHub Pages хранит всё в одном репозитории `gh-pages`.  
> Чтобы три ветки жили по разным URL, каждая публикуется в свою подпапку.

### `build.yml` — Проверочная сборка

**Триггер:** открытие Pull Request в `dev`, `stage`, `main`

Запускает `pnpm build` и проверяет, что проект вообще собирается без ошибок.  
Не деплоит — только проверяет. Защищает ветки от сломанного кода.

### `test.yml` — Тесты

**Триггер:** push и PR во все основные ветки

Запускает автоматические тесты проекта.

### `cta-email.yml` — Отправка CTA на почту

**Триггер:** вызов через `workflow_dispatch` (из кода сайта или вручную)

Запускает `scripts/send_cta.py` с данными из формы.  
Отправляет заявку на email клиента.  
Не уведомляет в Telegram (только этот воркфлоу).

### `telegram-notify.yml` — Уведомления в Telegram

**Триггер:** завершение любого воркфлоу (кроме `cta-email.yml`)

Отправляет сообщение в Telegram-бот с:
- Статусом (успех / ошибка)
- Названием воркфлоу
- Веткой и коммитом
- Ссылкой на запуск воркфлоу
- Описанием ошибки (если есть)

> Токен бота и ID чата хранятся в GitHub Secrets — никогда не коммитятся в код.

## CTA-форма и Python-скрипт

`scripts/send_cta.py` — Python-скрипт, который:
1. Принимает данные из формы (имя, телефон, сообщение)
2. Формирует письмо
3. Отправляет его на email менеджера через SMTP

Скрипт вызывается из GitHub Actions воркфлоу `cta-email.yml` при отправке формы на сайте.

> **Зачем Python, а не JS?**  
> Отправка email требует SMTP-доступа с секретными данными (логин/пароль).  
> Это нельзя делать на клиенте (в браузере) — данные будут видны пользователю.  
> GitHub Actions запускает скрипт на сервере GitHub — безопасно.
